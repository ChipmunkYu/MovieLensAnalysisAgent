# B部分架构图对应参考

> 用途：供A绘制作业二最终逻辑架构图时参考，确保图中覆盖P4–P6、D3–D4。本文只提供B负责部分的逻辑节点、箭头和编号关系，不单独作为最终架构图，也不指定具体产品或部署方式。

## 1. B部分需要在总图中表达的主线

```text
用户/前端提交治理请求
        ↓
Agent形成任务请求
        ↓
任务与状态管理创建逻辑任务、记录阶段和执行尝试（P4、P5、D3）
        ↓
数据处理能力执行可切分的检查、清洗和五维评分（P4、D3）
        ↓
各执行尝试生成相互隔离的候选结果（P5、D4）
        ↓
校验完整性与关键计数，并进行幂等发布（P5、P6、D4）
        ↓
结果服务只向Agent提供正式结构化结果和证据（P6、D4）
        ↓
Agent向前端返回真实结果及解释
```

核心含义：D3负责“任务如何执行、观察和恢复”，D4负责“哪份结果可以正式生效并被Agent读取”。

## 3. 建议标注的控制流

控制流使用与数据流不同的箭头样式，并在箭头上写明动作。

| 起点 → 终点 | 箭头标注 | 对应编号 |
| --- | --- | --- |
| 用户/前端 → Agent | 提交自然语言治理请求 | P6 |
| Agent → 任务与状态管理 | 创建逻辑任务，取得任务标识 | P5、D3 |
| 任务与状态管理 → 数据处理能力 | 调度阶段/分片；必要时失败重试 | P4、P5、D3 |
| Agent/前端 → 任务与状态管理 | 按任务标识查询总状态和当前阶段 | P4、P6、D3 |
| 任务与状态管理 → Agent/前端 | 返回排队、运行、成功或失败及原因 | P5、P6、D3 |
| 校验与发布能力 → 任务与状态管理 | 确认发布成功或校验失败 | P5、D3、D4 |
| Agent → 结果服务 | 任务成功后按结果标识读取正式结果 | P6、D4 |

## 4. 建议标注的数据流

| 起点 → 终点 | 箭头标注 | 对应编号 |
| --- | --- | --- |
| 原始数据区 → 数据处理能力 | 待检查/清洗的数据及版本标识 | P4、D3 |
| 数据处理能力 → 候选结果区 | 清洗候选数据、清洗前后指标、关键计数、异常样例 | P4、P5、D3、D4 |
| 候选结果区 → 校验与发布能力 | 被选中的候选结果及校验信息 | P5、D4 |
| 校验与发布能力 → 正式数据/质量结果/报告 | 幂等发布完整正式结果 | P5、P6、D4 |
| 校验与发布能力 → 结果清单与证据 | 任务、尝试、版本、计数和证据关系 | P6、D4 |
| 正式结果 + 结果清单与证据 → 结果服务 | 已发布结构化结果及来源信息 | P6、D4 |
| 结果服务 → Agent → 前端/用户 | 真实指标、报告和基于证据的解释 | P6、D4 |

## 5. 总图中必须保持的逻辑边界

1. **任务控制与实际数据分开**：任务与状态管理记录“做什么、做到哪里、是否成功”；原始数据、清洗数据和报告属于数据区域。任务元数据不能代替实际数据。
2. **逻辑任务与执行尝试分开**：一个逻辑任务可以因失败重试产生多个执行尝试，但最终只采用一个满足条件的成功尝试。
3. **候选结果与正式结果分开**：运行中、失败或未通过校验的输出只进入候选区；只有校验与发布能力可以使结果正式生效。
4. **计算事实与Agent解释分开**：数据处理产生结构化事实，Agent负责组织和解释事实，不负责创造状态、指标或版本信息。
5. **任务成功与结果发布分开**：执行尝试完成不等于结果已正式可见；只有完整校验并发布成功后，结果服务才能向Agent提供结果。

## 6. 与A部分节点的衔接

| A部分设计 | B部分衔接方式 |
| --- | --- |
| D1：元数据与数据读写分离 | “任务与状态管理、结果清单与证据”属于逻辑元数据；“原始数据、候选/正式清洗数据、报告”属于实际数据。总图可复用A的数据区和元数据区，不必重复画存储节点。 |
| D1：数据分级保护 | B的数据处理能力从A定义的原始数据区读取；候选结果可按可重算数据处理，正式报告和证据按正式产物保护。 |
| D2：数据集→任务→版本 | D2提供数据集、任务、规则和结果版本关系；D3增加执行尝试和状态；D4规定哪个尝试的候选结果可以成为某个正式版本。 |
| D2：正式结果不可变 | D4的幂等发布不能静默覆盖旧正式版本；合法的新治理任务形成新的发布记录或版本。 |

建议A在总图中共用“元数据/结果清单”和“实际数据区”，通过P、D编号同时标出双方决策，避免把同一职责画成两套组件。

## 7. 建议图例

- **实线框**：当前实验必须具备的逻辑角色或能力。
- **虚线框**：本次作业提出、后续实现的设计要求。
- **浅色框**：达到触发条件后再引入的未来能力，例如自动重试、阶段级恢复、慢任务备份执行和完整审计。
- **实线箭头**：数据流，标注传输的数据对象。
- **虚线箭头**：控制流，标注提交、调度、查询、重试或发布确认。
- 每个关键节点旁标出对应P、D编号，例如“任务与状态管理（P4、P5、D3）”。
